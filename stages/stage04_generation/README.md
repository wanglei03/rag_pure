# Stage 04:生成(带引用约束的 Grounded Generation)

## 这一层解决什么

检索到的资料如何变成"可信的答案"。核心矛盾:LLM 天生爱"编",
而知识库问答的第一要务是**不许编**。

## 代码位置

- `src/generation/prompts.py`:`RAG_SYSTEM` 指令(只用资料/必须标注引用/不足就说不知道)、`build_rag_messages`、`parse_citations`/`cited_chunks` 引用回收
- `src/generation/qa_chain.py`:`QAChain.ask()` = 检索 → 重排 → 生成 → 引用回收

## 关键设计

1. **指令约束**:system prompt 明确"只能依据资料;每条结论标 [n];资料不足就说'无法回答'"。
   注意:指令只是软约束,不能 100% 防幻觉——所以还要下面两道。
2. **引用标注**:让模型给结论标来源,用户可点击核查,体验上"可核查"就是信任的来源。
3. **引用回收 + 拒答检测**:`cited_chunks()` 只展示被实际引用的 chunk;`refused` 标志让产品层可以走"转人工/建议补充资料"的兜底逻辑。
4. **prompt 里的资料编号和展示编号一致**:模型说"[1]",用户看到的第 1 条就是那一块——细节,但真实项目里经常在这里出 bug。

## 运行

```bash
python stages/stage04_generation/demo.py
```

观察:问题 1 给出带引用的答案;问题 2 触发拒答(mock 模式下表现为"根据现有资料无法回答")。

## 面试高频问题

- **幻觉怎么治?** 三层:检索层(找全找准)、生成层(指令+引用+拒答)、评估层(忠实度指标在线监控,faithfulness 掉线报警)。只靠 prompt 是扬汤止沸。
- **答案错了怎么排查?** 先分锅:检索没召回(检索问题)→ 看 hit rate;召回了但模型没用(生成问题)→ 看忠实度;用户问题本身歧义 → 加澄清轮。RAG 调试的核心是**分段定位**。
- **chunk 塞几条?** 3~8 条常见。塞太多:token 贵、注意力稀释、无关内容诱发幻觉。
- **多轮对话的上下文怎么处理?** 简单做法:历史问题拼进检索 query;进阶:指代消解 + 独立问题改写。本项目单轮,面试可指出这是明确的扩展点。
