# Stage 07:评估(RAG 的"仪表盘")

## 这一层解决什么

"效果好不好"不能靠体感。评估体系让每一次改动(chunk 参数、换 embedding、加 rerank)
都有数据可依——这就是 JD 里"通过算法优化技术指标提升产品体验"的"技术指标"。

## 代码位置

- `data/eval/questions.json`:10 题评测集(问题 + 金标文档 + 金标答案要点)
- `src/eval/metrics.py`:检索指标(hit rate@k、MRR)+ 生成指标(忠实度、相关性,LLM-as-judge)+ 关键词覆盖
- `src/eval/runner.py`:跑对比表

## 关键设计

1. **两套指标互相印证**:
   - 检索指标不需要 LLM,便宜、确定、可回归;
   - 生成指标用 LLM-as-judge(忠实度:结论是否被资料支撑;相关性:是否答非所问);
   - 关键词覆盖(金标要点在答案中出现的比例)是不依赖任何模型的第三视角——三边互证,避免"裁判既是运动员"。
2. **对比实验驱动优化**:同一评测集跑四种检索方案,`hybrid+rerank` 那一行的提升就是优化工作的量化产出。
3. **评测集即资产**:真实项目里评测集来自线上 badcase 回填,持续扩充;每次发版前跑一遍,指标掉线阻断发布。

## 运行

```bash
python stages/stage07_evaluation/demo.py
```

mock 模式下:忠实度/相关性为固定演示分,**检索指标是真实计算的有效数字**(对 mock embedding 而言),对比表能真实反映四种检索方案的相对差异。

## 面试高频问题

- **RAGAS 和自建评估什么关系?** RAGAS 是这套思想的成熟框架版。自建一遍再去看 RAGAS,你会清楚每个指标在算什么、什么时候不可信(评委模型与被评答案同源时的偏向)。
- **LLM-as-judge 可信吗?** 有偏向(偏好长答案、偏好自家模型输出)。对策:评委与业务模型异构、固定评委版本、用非 LLM 指标(关键词覆盖)交叉验证、抽样人工复核。
- **hit rate 够了为什么还要 MRR?** hit rate 只看出没出现,MRR 还看出现得靠不靠前——排第 1 和排第 5 给模型的上下文质量完全不同。
- **线上指标怎么闭环?** 埋点收集点赞/点踩/重问率 → badcase 归因(检索/生成/资料缺失)→ 回流评测集 → 下一次迭代。评估不是一次性工作,是飞轮。
