# Stage 03:检索(向量 / BM25 / 混合检索 / 重排)

## 这一层解决什么

"把最相关的资料找全、排准"。这是 RAG 效果的最大变量,也是面试重点战区。

## 代码位置

- `src/retrieval/bm25.py`:jieba 分词 + BM25Okapi
- `src/retrieval/hybrid.py`:两路召回 + RRF 融合
- `src/retrieval/reranker.py`:重排接口 + 本地 OverlapReranker + HTTP 模型版

## 关键设计

1. **为什么要两路?** 向量检索把"年假/休假/请假"当近义词处理,但对"30 天""600 元"这类精确数字无感;
   BM25 相反。真实用户的问法两种都有,单路必翻车。
2. **RRF(Reciprocal Rank Fusion)**:分数 = Σ 1/(60+排名)。不看绝对分、不用归一化、不用调权重,k=60 是经典值。
3. **召回-重排两段式**:先宽召回(top 20),再精排(top 5)。双塔向量模型为了速度"query 和 doc 分开编码",精度有损失;
   交叉编码器 reranker 把 query+doc 一起进模型,更准但更慢,所以只用在几十个候选上。

## 运行

```bash
python stages/stage03_retrieval/demo.py
```

重点看第二个查询「出差结束后 30 天不报销会怎样」:向量路容易被"出差""报销"带偏,BM25 路靠"30"直接命中——融合后第一。

## 面试高频问题

- **RRF 和加权分数融合的区别?** 分数分布不同不可直接加权(余弦有界、BM25 无界);RRF 用排名,免调参、抗分数分布差异。
- **query 改写(query rewriting)做不做?** 用户问题口语化、多轮有指代,改写能显著提召回。做法:LLM 把问题改写成检索友好的关键词组合。本项目为聚焦未加,面试可主动提"下一步优化"。
- **rerank 模型放本地还是调 API?** API(bge-reranker-v2/gte-rerank)省事;数据敏感场景用本地 cross-encoder。判据:延迟预算 + 数据合规。
- **多路召回数量怎么定?** 经验值每路 20~50 候选,进 rerank 前 50 以内;最终给模型 3~8 条,塞太多浪费 token 还引入噪声。
