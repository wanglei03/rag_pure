# 面试讲解话术:RAG Agent 知识库项目(10 分钟版)

> 适用场景:中电信人工智能科技「大模型应用算法研发」岗项目介绍环节。
> 用法:每段话术可直接照读,方括号内是动作提示,不用念出来。

## 时间分配总览

| 段落 | 内容 | 时长 |
|---|---|---|
| 1 | 开场定位:一句话说清项目是什么、为什么做 | 30s |
| 2 | 场景与架构:业务背景 + 数据流 | 1.5min |
| 3 | 亮点一:检索优化(混合检索 + 重排,用指标说话) | 2min |
| 4 | 亮点二:可信生成(引用 + 拒答 + 评估) | 1.5min |

| 6 | 工程素养:可切换 provider、评估驱动开发 | 1min |

## 第 1 段:开场定位(30s)

「我准备的这个项目是一个**企业知识库问答系统**。做它的动机很直接:对准贵司星海产品线的典型场景——政企客户的大量制度、规范、产品文档,员工和客户的咨询重复度高,最适合用 RAG 落地。

我在这个项目里的目标不是调通一个 demo,而是**把 RAG 从解析到评估的全链路自己实现一遍**,并且每一层都做到可实验、可量化、可切换模型。整个项目约两千行代码,七个模块,我按数据流依次介绍。」

[要点:第一句给定位,第二句对齐对方产品线,第三句强调"自研"和"可量化", preempt "你这不就是调包吗"]

## 第 2 段:场景与架构(1.5min)

「业务场景:知识库里有五类文档——考勤休假、差旅报销、数据库变更规范、事故应急手册,还有一份模拟的产品白皮书。用户用自然语言提问,系统给出**带出处引用**的答案,答不了就明确拒答。

数据流分五层,我自下而上讲:

1. **入库层**:文档加载后按段落语义切分,每块约三百字、带标题元数据,向量化后存入向量库;
2. **检索层**:向量检索和 BM25 双路召回,RRF 融合,再用重排模型精排;
3. **生成层**:把检索结果组装进带强约束的 prompt,模型只能依据资料作答并标注引用;
4. **Agent 层**:工具调用循环,模型自己决定查知识库还是调计算器;
5. **服务化层**:知识库通过 MCP 协议封装成标准服务,任何 MCP 客户端即插即用。

架构上我想强调一点:**每层都是抽象接口**。向量库现在用 numpy 实现,换 Chroma 或 Milvus 不动业务代码;LLM 和 embedding 分开配置,因为 DeepSeek 这类供应商只有 chat 没有 embedding,生产上'生成用 A 家、向量化用 B 家'是常态——这是设计时就想清楚的。」

## 第 3 段:亮点一——检索优化(2min)

「检索是 RAG 效果的最大变量,我做的第一组实验在这里。

**问题**:纯向量检索对语义改写友好,但对'30 天不报销''600 元上限'这类精确数字和条款号不敏感;BM25 正好相反。真实用户的问法两种都有。

**方案**:双路召回 + RRF 融合。RRF 只看排名不看绝对分,因为两路分数分布根本不同——余弦有界、BM25 无界,直接加权需要大量调参,RRF 用经典的 k 等于 60,开箱即用。融合后再用交叉编码器思路的重排模型对几十个候选精排,把最相关的顶到最前面。

**结果**:我建了一个十题的评测集,每题标注金标文档,用 hit rate 和 MRR 做指标。对比四种方案——」

[此处打开 stage07 的检索对比表,指着讲]

「纯向量、纯 BM25、混合检索、混合加重排。结论是融合方案在这套评测集上检索指标最优。我更想讲的是**方法论**:不是'我觉得混合检索好',而是先建评测集、定义指标,再让每种方案用同一套数据说话——这也正对应岗位里'通过算法优化技术指标提升产品体验'的要求,指标就是技术指标,体验就是用户拿到正确答案的概率。」

[口径注意:mock embedding 下的绝对数字不要说死,表述为"在这套评测集上验证了链路正确性和相对优劣;接入真实 embedding 后用同一评测集回归,保证优化可复现"]

**预估追问:RRF 和加权融合的区别?** → 分数分布不同不可直接加权;RRF 免调参、抗分布差异,且对单路异常波动更鲁棒——一路翻车另一路还能撑住排名。

## 第 4 段:亮点二——可信生成(1.5min)

「检索到了只是第一步,知识库问答的第一要务是**不许编**。

我做了三道防护:第一道,指令约束,prompt 明确'只能依据资料、每条结论标引用、资料不足就说无法回答';第二道,引用回收,模型标注的 [n] 会解析回来,只把被实际引用的资料展示给用户,编号一致可核查;第三道,拒答检测,识别'资料不足'类回答,产品层可以走转人工或建议补充资料的兜底。

为什么要三道?因为指令只是软约束,单靠 prompt 防幻觉是扬汤止沸——这对应我评估体系里的**忠实度指标**:用一个评委模型判断每个结论是否被资料支撑,和关键词覆盖这种不依赖模型的指标互相印证,避免'裁判运动员同体'。」

**预估追问:线上答案错了怎么排查?** → 先分锅再下药:检索没召回看 hit rate,召回了模型没用看忠实度,问题本身有歧义就加澄清轮。RAG 调试的核心是分段定位,一把梭的 prompt 调优效率最低。

## 第 5 段:亮点三——Agent 与 MCP(2min)

「固定 pipeline 解决不了的问题:用户一个问句里可能既查制度又算金额。我在 Agent 层做了**结构化决策循环**:每次让模型在'调工具'和'给最终答案'之间输出一个 JSON,外层循环解释执行、把观测结果回填,模型再决策。比如'上海住宿上限乘以三晚'这个问题,轨迹是查知识库拿到 600 元,再调计算器算 1800,最后汇总。

选 JSON 决策而不是自由文本 ReAct,是因为可解析、可校验、可回放评估,而且任何模型——包括本地 ollama——都能跑,不依赖供应商的原生 function calling。

**MCP 是项目里我投入最多的部分**:把知识库检索、计算器封装成 MCP server,stdio 传输,理论上 Claude Desktop、Qoder 任何 MCP 客户端配一行就能挂载。这里有两个我实际踩掉的坑,都是教科书上学不到的:

第一,stdio 模式下 **stdout 就是协议通道**,知识库加载的日志如果不处理会直接污染协议流,我的解法是加载时重定向;

第二,也是最痛的:Windows 上 **numpy 不能在 MCP 事件循环的异步 handler 里首次 import**——BLAS 线程初始化和 anyio 工作线程死锁,症状是 tools/call 收到请求后永不返回。我用二分法把死锁定位到 import 语句,解法是模块加载时就饥渴初始化,把重活全部挡在事件循环启动之前。这个问题我在 GitHub 的 issue 里验证过不是个例。」

[要点:MCP 这段的亮点是"踩坑-定位-解决"的完整闭环,体现真实工程能力;语速放慢,这是 differentiate 的部分]

**预估追问:Agent 和 LangChain 什么区别?** → 思想相同,我这是最小实现。正因为自己实现过循环、观测回填、步数上限这些机制,用框架时才知道轨迹跑偏该改哪里,而不是只会调参。

**预估追问:MCP 和 function calling 什么关系?** → 互补的两层:function calling 是"模型发起结构化调用"的能力,MCP 是"工具如何被发现和暴露"的协议。模型通过 MCP 发现工具,通过 function calling 发起调用——类比 USB-C 和充电协议。

## 第 6 段:工程素养(1min)

「项目的可复现性我也做了设计:**离线 mock 模式**。没有网络、没有 API Key 时,LLM 和 embedding 都有确定性的 mock 实现,全链路——包括 Agent 决策和评估流程——都能跑通,保证演示和测试不依赖外部条件;一行环境变量切到 DeepSeek 或千问。

这背后是工厂模式和依赖注入:业务代码只依赖抽象接口,五十行代码完成了很多人用一整套模型网关做的事。」

## 第 7 段:边界与规划(1min)

「这个项目的边界我清楚,也规划了下一步,主动讲出来:

- 目前是单轮问答,**多轮指代消解和 query 改写**是明确的扩展点,用户口语化提问对召回率影响最大;
- 向量库是暴力检索,数据量上到十万级 chunk 后需要换 HNSW 索引,接口已经预留;
- 表格和图片解析没覆盖——这是生产 RAG 最大的坑之一,版式还原加 OCR 是政企文档落地的关键路径;
- 评估集目前十题,真实场景应该从线上 badcase 持续回填,形成评估飞轮。

如果把这个项目推进到生产,我下一步会优先做 query 改写,因为在检索、生成、评估三段里,它的预期收益成本比最高。」

[要点:主动讲边界 = 诚实 + 有判断;"收益成本比最高"体现产品 sense,对应 JD 第二条]

## 第 8 段:收尾(30s)

「总结:这个项目我用两千行代码走通了'文档进、可信答案出'的完整链路,并且每一层都有指标、有实验、有踩坑记录。代码和七个阶段的文档都在我的仓库里,七个 stage 可以逐个现场跑。

我特别想深入聊的是检索优化或者 MCP 工程化这两块,各位老师感兴趣哪个方向?」

[最后一问把主动权交回去,引导面试官进入你准备最充分的领域]

## 附:高频追问速答卡

1. **chunk size 怎么定的?** —— 没有银弹。经验值中文 200-400 字;工程做法是固定 20-50 个典型问题,用不同参数跑 hit rate 选优。我在 stage01 做了 160/280/450 的对比演示。
2. **为什么不直接用 LangChain/LlamaIndex?** —— 学习阶段自研一遍才知道框架在替你做什么;生产上会用成熟框架,但调试和定制的能力来自对原理的理解。
3. **rerank 模型选 API 还是本地?** —— 看延迟预算和数据合规。API 省事;政企私有文档用本地 cross-encoder,这也是星海这类私有化交付的典型诉求。
4. **评测集怎么建的?** —— 从文档倒推 10 个真实员工会问的问题,标金标文档和答案要点;生产上从线上 badcase 回填。
5. **LLM-as-judge 可信吗?** —— 有偏向(偏好长答案、自家模型)。对策:评委异构、版本固定、非 LLM 指标交叉验证、抽样人工复核。
6. **MCP 的安全边界?** —— server 侧工具白名单,敏感参数环境变量注入,生产加鉴权和审计。
7. **幻觉怎么治(再被追问)?** —— 三层:检索层找全找准、生成层指令加引用加拒答、评估层忠实度在线监控掉线报警。
8. **如果知识库很大,向量库怎么选?** —— 万级暴力扫;十万级 HNSW(FAISS/Chroma);百万级 Milvus/pgvector 带过滤;选型看数据规模、过滤需求、运维成本。
